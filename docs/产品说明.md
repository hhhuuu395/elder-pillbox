# 智能药盒第一版：把"建计划"的成本降到零

**场景选择：A｜老年人 × 长期用药**

---

## 1. 核心用户

第一版先服务"帮老人管理用药的子女"，而不是老人本人。

场景设定：一位 70 岁上下、能独立生活的老人。让他自己完成"录入 5 种药品信息"这种操作并不现实；
真实家庭中的分工往往是——子女一次性代录入，老人每天只做"按提示吃药"这一件事。
所以第一版的产品形态是：**子女负责配置，老人负责执行**。
这个分工的适用边界：它默认"子女能在首次配置时到场（或远程可协助）"。
如果这个前提不成立（老人独居且子女无法到场），就需要第二录入通道——
语音描述录入、药品条码扫描等，属于第二版的范围，第一版不做。

## 2. 核心问题

**老人不缺提醒，缺的是一份可靠的用药计划。**

手机闹钟早就解决了"到点响"的问题，但老人依然漏服，原因在于：
- 5 种药、不同剂量、不同频次（每日一次/两次/隔天），靠记忆和纸条维护极易出错；
- 老人几乎不可能自己把医嘱、说明书转成一份结构化的每日计划；
- **计划不存在，后面一切提醒功能都是空谈。**

因此第一版只解决一件事：**把用药计划的建立成本降到接近零，并把计划
呈现为老人看得懂的"今天该吃什么"一屏。**

明确不做的：复诊管理、药品百科、用药统计图表、多角色社交功能。

## 3. 核心流程（一条主线走完）
子女拍药盒/说明书（Mock OCR）
↓
AI 抽取 → 结构化用药计划（药名 / 剂量 / 频次 / 疗程）
↓
子女确认 / 补全缺失字段（人工确认后才生效）
↓
老人端：今日药历（当前时段高亮，大字体）
↓
按时打卡 → 状态更新
↓
超时未服 → 出现状态选择：已带出 / 补服 / 确实漏服
           ├─ 已带出：状态挂起，不计漏服
           ├─ 补服：打卡流转，不计漏服
           └─ 确实漏服 → 标记漏服 →（模拟）通知子女



## 4. 智能能力：AI 在哪一步参与，为什么

AI 只在一个点参与，且刻意不放在"决策"环节：

| 参与点 | 做什么 | 为什么 |
|---|---|---|
| 计划抽取（核心） | 把药盒上的非结构化文字 → 结构化用药计划 JSON | 这是人工最痛苦的环节，而 AI 做的只是"搬运 + 格式化"，不涉及任何医疗判断，天然安全 |

漏服通知的文案由固定模板生成，不经过 AI。

漏服状态的设计逻辑：提醒只是手段，按时服药才是目的——系统不把
"错过提醒"直接等同于"漏服"，给用户留出"带出/补服"的真实出路。

**AI 刻意不做的事**：不识别疾病、不推荐药品、不建议调整剂量——
计划生成后必须经人工确认才生效，AI 输出永远只是"草稿"。

## 5. 关键假设（当前最重要、尚未验证）

> **假设：子女愿意用"拍照代替手输"完成录入，且 AI 抽取的准确率
> 足以让"确认修改"的成本显著低于手工输入。**

如果这个假设不成立（例如抽取错漏太多、确认比手输还累），
整个产品的核心价值就不存在。

## 6. 边界与 Mock 说明（对应题目"统一边界"）

- 药品、用药计划、剂量视为已确定，**不做疾病诊断、药品推荐、治疗方案调整**；
- OCR 为 Mock：点击"拍照"返回一段固定的药盒文字；
- AI 抽取为**真实调用**（LLM 解析为 JSON），其余硬件/通知均为 Mock。

## 7. 异常与边界情况处理（题目"另需"项）

选择处理：**AI 抽取结果不可靠**
- 返回 JSON 缺字段 / 格式错误 → 不生成计划，界面高亮缺失字段，强制人工补全；
- 频次模糊（如"遵医嘱"）→ 不猜测，要求用户手动明确填写；
- 设计原则：**AI 不确定的，宁可让用户多填一步，也不生成一份看起来完整但错误的计划。**

## 8.考虑过、但不放进第一版的问题

产品探索中识别出三个真实问题，经取舍后均不进入第一版，理由如下：

① 老人不会拍照
不构成第一版的问题——拍照的是子女而非老人（见第 1 节分工设计）。
真正的边界问题是"子女无法到场配置"，解法（语音/条码录入）归入第二版。

② 老人出门错过提醒
这是真实高频场景，已用最小成本回应：漏服前增加"已带出 / 补服"状态
（见第 3 节流程），不做更重的方案（如随身分药格、外出模式），因为
那需要硬件形态配合，超出软件原型能验证的范围。

③ 药箱丢失

丢的是设备：在完整产品形态下，数据与用药计划存于账号云端，换设备登录即可恢复——
这是智能药箱相对普通药盒的天然优势，不需要额外设计
（当前 Demo 是无账号、纯内存实现，重启即清空，这一条尚未落地）；
丢的是药：属于"补药/遗失处理"场景，超出"建立计划+今日执行"
的第一版范围。

## 9. Demo 说明

- 技术栈：FastAPI（单文件后端 + API 代理）+ 单页 HTML（大字体、老年友好 UI）
- AI 调用：DeepSeek API（key 仅存在于后端，不暴露给前端）
- 运行方式：见 `README.md`

---

*使用的 AI/Coding 工具：Claude Code（编码）+ DeepSeek API（产品内智能能力）*
*实际投入时间：约 6 小时（跨 2 天）*
