# 老人药盒助手 · 复盘

## 一、项目是什么

老人药盒助手是一个面向独居老人服药场景的 Demo，分老人端和子女端两个界面，跑在同一个页面上、用 `?view=` 参数区分。

- **老人端**：按早上、中午、晚上三个时段展示当天要吃的药，大字版。某顿到点没吃就标红，并给老人三个选项：带出门了、现在补吃、这顿确实没吃。
- **子女端**：远程收到漏服通知，不用守在老人身边。
- **AI 录入**：处方不用手打，拍一张照片让 AI 识别成结构化字段，再由人核对确认。

技术上，后端是一个 FastAPI 单文件（`app.py`），前端是一个 HTML 单页（`static/index.html`），另有一个 `curl_checks.sh` 做接口回归测试。

## 二、核心设计：AI 打草稿，人来签字

这个项目最想表达的一点是：**AI 在医疗场景里只能是草稿，不能是终稿。**

所以 AI 的职责被压得很窄——只负责把处方照片上的文字转成结构化字段，**不负责判断**。遇到"遵医嘱""按说明书"这类它拿不准的写法，要求它老老实实留空，绝对不许猜。留空不是失败，编造才是。

AI 填完只是草稿。凡是有空缺的地方，系统会标成警告、并且**卡住"确认并生效"按钮**，人必须补全了才能提交。人签字之后，这份药单才会出现在老人端。

为了让"AI 会出错"这件事看得见，我做了三种 AI 返回模式：

| 模式 | 作用 |
|---|---|
| `normal` | 真实调用 DeepSeek |
| `missing_fields` | 内置 mock，专门复现"AI 多识别出一味原文里根本没有的维生素C"这种事故现场 |
| `malformed` | 内置 mock，模拟 AI 返回非法 JSON |

这三种模式不只是为了实现功能，更主要的作用是**把"AI 不可靠"从一句抽象的话，变成一个能当场演示、能反复重放的场景**。答辩的时候我不需要口头解释"AI 可能会错"，直接切到 `missing_fields` 档，错误就出现在屏幕上了。

## 三、从 0 到现在的时间线

**第一阶段：搭核心功能。**
用 FastAPI + 前端单页搭起三个模块——老人端服药、子女端通知、AI 拍照识别。同时把三种 AI 返回模式做出来，尤其 `missing_fields` 档，它存在的意义就是复现"AI 多识别一味维生素C"的事故现场。

**第二阶段：虚拟时钟。**
真实场景里，要演示一次漏服得等好几个小时，根本没法在答辩现场演示。所以做了虚拟时钟，手动拨时间，几秒钟就能让药变成超时标红。这是纯粹为了"能不能演示"而做的设计。

**第三阶段：写接口回归测试。**
写了 `curl_checks.sh`，一共 32 项接口断言。最终结果 **PASS 32 / FAIL 0**。

**第四阶段：排障。**
把服务从 8001 端口换到 8000 之后遇到了异常，最后发现其实是两个互不相干的问题凑在一起：

1. AI 模式被切到了真实调用档，但没配 API Key；
2. 用药计划消失了——因为状态存在服务内存里，**进程重启就清空**。

第二个问题让我第一次认真想"为什么 demo 用内存、产品要用数据库"。

**第五阶段：配置 DeepSeek Key 踩坑。**
先是发现环境变量只对设置它的那个终端会话生效——`export` 和启动服务必须在同一个窗口里，否则配了等于没配。解决了之后，真实调用仍然报"调用 DeepSeek 失败："，而且**冒号后面是空的**，什么信息都没有。

**第六阶段：借助 Claude Code 定位根因。**
这个空报错最后查出来是：本机代理软件（Clash）注册了系统代理 `https://127.0.0.1:7897`，而 Python 的 httpx 默认 `trust_env=True`，会去读注册表里的代理设置，于是对着一个只讲明文 HTTP 的本地代理做 TLS 握手，连接直接断掉。

两个关键细节：

- **curl 不读注册表**，所以出现了"curl 能通、Python 不通"这种反直觉的现象；
- 报错为空，是因为这类 `ConnectError` 异常的 `str()` 本身就是空字符串，而老代码只取了 `str()`。

**第七阶段：修复与验证。**
修复动作：httpx 改成 `trust_env=False` 直连（DeepSeek 是国内服务，直连是合理的）；补全错误透传和终端日志；Key 移进 `.env` 自动加载（手写解析，没有引入 python-dotenv，省一个依赖）；确认 Key 不出现在前端响应里、也不出现在任何被 git 跟踪的文件里。

修复后验证：真实调用 DeepSeek 成功解析出药品；用坏 key 测试能报出 401 和完整信息；`curl_checks.sh` 32/32 PASS；端到端 15/15 通过；并用 `git diff` 确认 mock 逻辑零改动。

## 四、踩坑与学到的东西

**1. 内存态 vs 持久化。**
重启丢数据这件事，让我第一次具体地理解了"demo 用内存、产品用数据库"不是一句套话，而是两种完全不同的假设。内存态默认了"进程一直活着"，而真实产品里这个假设根本不成立。

**2. 环境变量是会话级的。**
"配置了"和"生效了"是两回事。`export` 只影响当前终端窗口，换个窗口启动服务就没了。更稳的做法是 `.env` 跟着项目走、启动时自动加载——不依赖"我记不记得在正确的窗口里敲过那行命令"。

**3. "报错信息为空"是一条线索，不是终点。**
空报错一开始让我以为是 Key 的问题（鉴权失败通常报错很明确）。后来才明白：**空报错是传输层故障的指纹**——真的是 401 的话，会带着完整的报错信息回来。所以看到空报错，第一反应应该是往网络层查，而不是往鉴权查。

**4. 两套环境行为不一致，要警惕。**
curl 通但 Python 不通，同一个网络、同一个地址，结果却不一样。差异藏在一个很容易被忽略的地方——"谁读系统代理"。这种时候不能笼统地说"网络有问题"，得问清楚：**是哪一层、在什么条件下**不通过。

**5. 演示可靠性是一种工程决策。**
主演示用 mock，真实调用只做一个短彩蛋。原因很实际：mock 确定、免费、可复现；真实调用有网络波动、有费用、还有延迟，在答辩现场是不可控因素。把不可控的东西放小、放边上，是设计的一部分。

**6. Key 安全。**
做过的处理：泄露过的 key 作废重新生成；新 key 写进被 `.gitignore` 忽略的 `.env`；接口只返回"有没有配置"的布尔值，绝不返回明文。

## 五、未来计划

1. **用药计划持久化到 SQLite**——先把"重启就丢"解决掉。
2. **老人端语音提醒**——老人看字不如听声，语音播报比界面更贴近真实使用场景。
3. **接入真实 OCR**——现在拍照那一步是模拟的，换成真的 OCR 才算闭环。
4. **子女端多老人管理**——一个子女可能要照顾不止一位老人。

## 六、一句话总结

这个项目让我完整走了"功能开发 → 演示设计 → 排障 → 借助 AI 工具修复 → 安全收尾"的流程，最大的收获是把"AI 会出错"从抽象认知变成了系统里一条可演示的安全设计。
